# 첫 게시 패킷

작성 기준: 2026-10-24. campaign_id: MU-KO-001 / experiment_id: EXP-MU-KO-001.
상태: 검토 가능한 초안 완성, 채널·계정 미확정, 외부 게시 미승인·미실행.

## 잠정 채널과 목적

잠정 후보는 **Disquiet에서 Mu 제품 등록 심사 후 제품에 연결하는 포스트(조건부)**다. 2026-10-24 확인한 [공식 리뉴얼 공지](https://disquiet.io/announcement)에 따르면 기존 메이커로그의 신규 작성은 중단되었고, 본인이 만든 제품을 먼저 등록해야 한다. 제품은 작성 → 검토 요청 → 승인 절차를 거치며, 메인 피드에는 제품에 연결된 포스트가 노출된다. 예전 메이커로그 안내를 현재 실행 경로로 사용하지 않는다.

Mu처럼 사전 신청 단계인 제품의 등록 허용·승인 여부, 게시 계정, 링크 지원은 미확인이다. 식당 예약 ICP가 해당 채널에 있다는 근거도 아직 없으므로, 채널 확정이나 고객 검증 완료로 기록하지 않는다. 제품 등록 승인 전에는 위 대표 게시물과 아래 질문을 Disquiet에 게시할 수 있다고 가정하지 않는다.

고객 원문에 광고 댓글을 남기는 방식은 사용하지 않는다. 오마카세 갤러리는 [공지](https://gall.dcinside.com/mgallery/board/view/?id=omakase&no=189249&page=1)에 광고 제재가 명시되어 직접 홍보 후보에서 제외한다.

핵심: 인기 식당 예약 확인으로 관심 → 범용 모바일 앱 자동화 비서 Mu → 사전 사용 신청. 팀이 소개하는 제품임을 공개하고, 실제 사용 후기나 검증된 데모처럼 표현하지 않는다.

## CTA와 귀속 — 내부 기록

제품 설명은 한국어 랜딩으로 연결하고, 신청 CTA는 수신처가 확인된 메일 작성 링크에 캠페인 코드가 포함된 제목을 넣는다. 별도 폼이나 랜딩 변경은 필요하지 않다.

- 수신처: support@pairful.ai (공개 신청 경로 확인).
- 사전 입력 제목: `[MU-KO-001] 무 먼저 써보고 싶어요`.
- 공개 CTA의 mailto는 subject만 채운다. 본문은 강제하지 않는다.
- 메일 작성 화면 열기·버튼 클릭은 신청 완료가 아니다. 실제 수신 확인 후 제외·중복 제거·귀속을 적용한다.
- 기존 `/w/go/ko`에 캠페인 쿼리를 추가하는 것만으로는 메일 제목·본문에 코드가 보존되지 않았다. 확인 증거: [CTA HTTP 점검](../ref/evidence/mu-cta-20261024.json).
- 해당 채널이 mailto 링크를 허용하고 정상 표시하는지는 게시 전 미리보기에서 확인해야 한다. 링크를 허용하지 않으면 제목 코드 수동 입력 안내로 바꾸고 **본문 해시·asset_id를 다시 계산한 새 검토본**을 만든다. 현재 승인본을 임의 변경한 채 게시하지 않는다.
- 코드 누락 신청은 이 콘텐츠의 전환으로 자동 분류하지 않는다. 추가 출처 확인 없으면 출처 불명으로 둔다.
- 콘텐츠별 태그는 넣지 않았으므로 현재 귀속은 캠페인 단위다. 여러 콘텐츠의 개별 성과 비교에 사용하지 않는다.

메일 링크를 지원하지 않는 채널에서 사용할 복사 대안(현재 공개 본문에는 미적용):

이 대안을 넣으면 공개 본문이 달라지므로 위 링크형 초안과 별도 검토하고 hash/asset_id를 다시 계산한다.

## 콘텐츠 식별과 정확한 승인 범위

이 패킷은 **제목 + LF 두 개 + 공개 본문**의 UTF-8 바이트를 해시한다. 마지막 개행은 포함하지 않는다. PUBLIC_BODY 주석 및 내부 기록은 공개 본문에 포함하지 않는다.

- asset_id: `MU-KO-001-A-7e8efe601a3cbc5b`
- content_sha256: `7e8efe601a3cbc5b68f07aae854923b76257579a12e1b987c7724bb201f20a53`
- channel: `pending` (잠정 후보: Disquiet Mu 제품 등록 심사 후 제품 연결 포스트)
- account_ref: `pending`
- approval_status: `pending`
- publication_status: `not_posted`
- published_url: `null`
- published_at: `null`

현재 `src/loop.py`는 `config.draft.body`만 해시한다. 메인 통합에서 제목과 본문을 위 직렬화 방식으로 합쳐 `draft.body`에 반영했고 hash/asset_id 일치를 확인했다. 초기의 짧은 합의 문안은 별개 콘텐츠이며 승인을 재사용하지 않는다. 첨부물은 현재 없고, 추가 시 첨부물까지 포함한 최종본을 별도로 검토해야 한다.

## 고객 문제 질문 1개 — 내부 제안, 대표 게시물과 별개

아래는 신규 계정이 자기 채널에 단독으로 올릴 수 있도록 준비한 질문이다. 실제 채널의 제품 관련 질문·홍보 규칙과 사용자의 게시 승인을 확인한 뒤 사용한다. 다른 고객의 글에 광고 댓글로 붙이지 않는다.

> Pairful의 Mu를 만드는 팀입니다. 카카오톡으로 모바일 앱 작업을 부탁하는 비서를 준비하며, 식당 예약 때 어떤 일이 번거로운지 알아보고 있어요.
>
> 최근 인기 식당을 예약하려고 할 때 가장 번거로웠던 건 무엇인가요?
>
> ① 앱을 열고 날짜·인원을 바꾸며 가능한 시간을 확인하는 과정
> ② 원하는 시간에 자리가 없거나, 예약 오픈 때 경쟁해야 하는 상황
>
> 둘 다 겪으셨거나 다른 경험이 있다면 편하게 들려주세요.

질문 응답은 조사 신호로만 기록한다. 사전 신청의 필수 조건이나 신청 완료로 취급하지 않는다. ①의 응답은 구체적인 최근 경험을 읽고 조회 수고의 근거인지 판단한다. ②만으로 Mu의 조회 위임 수요가 있다고 해석하지 않는다. 답변에 개인 신상·예약 번호·결제 정보를 요청하지 않는다.

## 새 계정에서의 도달 경로 준비

새 계정 생성만으로 노출을 기대하지 않는다. 먼저 제작자·제품 소개와 제품 링크로 정체성을 확인할 수 있게 하고, 대표 소개 게시물을 둔다. 이후 제품 관련 질문이 허용된 자기 채널에서 위 질문으로 경험을 듣고, 관심 있는 사람이 프로필과 제품 소개를 스스로 확인할 수 있게 연결한다.

초기 노출 경로는 별도로 확인해야 한다. 제품 연결 포스트로 메인 피드에 노출될 조건을 갖춰도 인기 식당 예약 ICP가 실제로 도달했는지 미확인이므로, 조회·응답·실제 신청을 구분한다. 계정이 준비되면 첫 게시의 노출 여부부터 확인하고, 노출이 부족할 때는 메시지 효과를 판단하지 않는다. 관심 응답을 근거로 개인 메시지·메일·반복 홍보를 자동 발송하지 않는다.

위 프로필과 질문은 별도 초안이며 기존 대표 게시물의 제목·공개 본문·content_sha256·asset_id를 변경하지 않는다. 질문을 실제 게시할 때는 별도의 asset_id와 승인·게시 영수증을 남긴다.

검토 순서: 계정·제품 관계 확인 → 등록 문구와 제품 단계 확인 → 사용자 승인 범위 내 등록·검토 요청 → 플랫폼 승인 확인 → 제품 연결 포스트의 미리보기·링크 확인 → 정확한 본문과 계정에 대한 게시 승인. 각 단계의 실제 실행과 승인은 별도로 기록한다.

채널 근거와 제외 사유는 [고객·채널 조사](../ref/customer-channel-research.md)를 함께 읽는다. 계정 생성만으로 도달을 예상하지 않으며 제품 심사 대기 시간이나 메인 피드 노출량을 보장하지 않는다.

사용자가 2026-10-24 실제 게시 전 검토를 명시적으로 요구했다. 위 최종 제목·본문·첨부물(현재 없음)·링크·채널·계정 전체를 보여준 뒤 승인을 받는다. 내용이나 대상 변경 시 다시 검토한다. 이 파일의 완성이나 전략 동의는 실제 게시 승인이 아니다.
