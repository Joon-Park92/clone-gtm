# 보조 콘텐츠 검토 — 최적화 목표가 아님

이 문서는 기존 콘텐츠 Rubric을 보조 검토로 보존한다. **수정할 대상을 정하는 근거는 실제 사용자 반응과 신청 결과**이며, 문안 점수만으로 새 실험을 만들지 않는다. 최신 주 판단 기준은 [반응 기반 Rubric](rubric.md)이다. 이전의 CTA 단순화 제안은 실제 반응으로 검증되지 않은 편집 가설이며 우선 실행 과제가 아니다.

# Mu 루프의 판단과 개선 기준

목적은 매일 새 글을 만드는 것이 아니라, 실제 신청으로 이어질 가능성에 관한 불확실성을 한 가지씩 줄이는 것이다. 주 지표는 캠페인 귀속 신규 사전 신청자 수로 고정한다. Rubric 점수는 콘텐츠의 준비 상태이며 수요·전환 성과가 아니다.

## 두 개의 피드백 루프

1. 게시 전: 관측 근거 → 초안 평가 → 약점 하나 → 수정 가설 → 한 조건 수정 → 같은 기준 재평가 → 유지 또는 사람 검토 후보.
2. 게시 후: 실제 도달·반응·신청 → 측정 신뢰도 확인 → 이전 예측과 비교 → 유지/추가 관측/수정/집계 감사 → 다음 실험.

작성과 비평은 같은 에이전트의 별도 단계로 수행한다. 비평 단계에는 초안·제품 근거·이전 관측을 주고 작성자의 자기평가를 근거로 인정하지 않는다. 같은 모델의 두 단계는 독립된 고객 검증이 아니므로 실제 반응과 사람이 최종 교정한다.

## 게시 전 Rubric v1: mu-content-v1

각 판단에는 원문 또는 초안 인용, 출처, 관측, 이유를 붙인다. 근거가 없으면 null이다. 점수를 합산하거나 평균내어 약점을 숨기지 않는다.

| 항목 | 0 | 1 | 2 |
| --- | --- | --- | --- |
| 고객 상황 customer_situation | 대상과 작업이 드러나지 않음 | 식당 예약 등 넓은 문제만 있음 | 날짜·인원 등 조건과 앱에서 확인하는 행동이 구체적 |
| 위임 가치 delegation_value | 예약 성공·희소 좌석만 강조 | 편리함을 말하나 맡길 작업이 모호 | 직접 앱을 확인하는 일 → 채팅 요청 → 확인 결과가 연결됨 |
| 제품 정직성 product_honesty | 검증되지 않은 즉시 이용·성공을 약속 | 현재 상태 또는 제품 범위가 모호 | 사전 사용 단계와 앱 작업 비서라는 범위를 명확히 전달 |
| CTA 명확성 cta_clarity | 신청 행동·경로 없음 | 신청과 댓글 등 여러 행동이 경쟁하거나 경로 모호 | 신청이라는 주 행동 하나와 실제 안내 경로가 명확 |

이는 문구의 명료성 평가다. 고객 상황 항목이 2여도 실제 위임 수요가 검증된 것은 아니다. 모든 앱에서 성공한다거나 모바일에서만 예약할 수 있다는 미검증 단정은 쓰지 않는다.

점수보다 먼저 확인하는 사실 조건:

- claims_supported: 공개 주장마다 제품 근거가 있고, 실제 동작 확인 여부와 표현 수준이 맞는가? 제품 소개문은 소개 내용의 근거이며 실제 기능 성공 증거는 아니다.
- early_access_clear: 즉시 이용을 기대하게 하지 않고 사전 사용 신청 상태를 밝히는가?

fail이면 사실 표현부터 고치고 새 기준본으로 다시 평가한다. unknown이면 근거 확보 또는 해당 주장 삭제를 제안한다. 이 과정은 전환 개선 실험으로 집계하지 않는다.

## 수정 선택과 종료

사실 조건을 통과한 뒤 가장 낮은 항목 하나를 고른다. 동점은 고객 상황 → 위임 가치 → 제품 정직성 → CTA 순서로 처리한다. 이는 운영용 우선순위이며 시장의 법칙이 아니다.

수정 제안에는 부모/후보 본문 해시, target_criterion, changed_variables 한 개, 가설, 예상 관측, 다음 관측 방법, 중단 조건, 유지할 조건, 시도 횟수를 기록한다. 비교 시 동일 Rubric 버전과 동일 근거 범위를 사용한다. 타깃 점수 상승과 다른 항목의 비하락을 확인해야 사람 검토 후보가 된다. 자동 게시 승인이 생기지는 않는다.

한 기준본에서 최대 2회 수정한다. 이미 전 항목 2이면 점수를 위해 재작성하지 않는다. 근거 부족·퇴행이면 유지 또는 추가 조사, 예산 소진이면 사람 검토로 넘긴다. 횟수는 부모 기준본에 연결된 이력에서 산출하며 모델이 임의로 1로 되돌릴 수 없다. 현재 코어는 전달된 횟수의 상한과 단일 변경 선언을 검사하고, 실제 수정 범위·누적 횟수 검증은 런타임/최종 검토 책임이다.

## 실제 성과 판단

| 관측 | 판단 | 다음 행동 |
| --- | --- | --- |
| 기간·귀속·접수·기존 신청자 기준 미확인 | 효과 판단 불가 | 측정 연결 또는 검증 |
| 같은 누적 값·새 근거 없음 | 유지 | 같은 자료로 다시 수정하지 않음 |
| 노출 부족 | 메시지 효과 판단 보류 | 도달 경로 한 가지 점검 |
| 도달은 있으나 방문 부족 | 메시지 또는 대상 적합성 가설 | 실제 표현·링크·도달 대상 확인 후 한 변수 제안 |
| 방문은 있으나 신청 부족 | 설명·신청 마찰·추적 오류 가설 | 병목 하나 확인; 제품 거절로 단정하지 않음 |
| 새 귀속 신청 관측 | 관심 신호 | 유지 가능성을 먼저 검토하고 같은 문제의 후속 가설 제안 |
| 누적 신청 감소 | 집계 정정 가능성 | 제외·귀속 정정 근거 감사 |
| 표본 부족·기간/유입 조건 차이 | 비교 불충분 | 관측 연장 또는 비교 한계 기록 |

100회 노출/20회 방문은 설정 파일의 초기 운영 가정이며 통계적 유의성 기준이 아니다. 코어의 next_action은 원인 확정이나 자동 수정 명령이 아닌 진단 후보다. 현재 단순 코어는 누적 신청이 양수이면서 증가하지 않으면 관측 유지를 권한다. 신규 보조 지표·정성 근거를 이용한 상세 재진단은 에이전트 단계에서 수행한다.

자기평가가 좋아졌지만 고객 반응이 달라지지 않으면 ‘전환 개선 미확인’으로 기록한다. 실패한 예측도 보존한다. 다음 실험에서는 가설·표현·배포 중 주요 변수 하나만 바꾼다. 캠페인 수준 귀속만 가능하면 콘텐츠별 승자를 선언하지 않는다.

## 학습 기록 계약

매 실행에 아래를 남기고 이전 기록을 덮어쓰지 않는다.

- observation: 기간·표본·숫자 또는 실제 발언·증거 참조, 미측정 항목
- diagnosis: 병목 가설, 다른 설명, 확신하지 못하는 이유
- prediction_review: 이전 예상, 실제 관측, 일치/불일치/판단 불가
- decision: retain / observe / revise / audit와 근거
- experiment: 바꿀 변수 하나, 유지 조건, 예상 관측, 중단 조건
- revision: 부모/후보 해시, 같은 버전의 전후 평가, 시도 횟수, 검토 상태
- next_observation: 시각·담당·필요 자료

Rubric을 고쳐 실패를 성공으로 바꾸지 않는다. 기준을 바꿀 필요가 있으면 실패 사례와 제안 이유를 남기고 사용자 검토 후 새 버전으로 시작한다. KPI·사실 조건·게시 승인 권한을 에이전트가 스스로 완화하지 않는다.

## 현재 문안에서 시작할 개선 가설

현재 Threads 초안에는 신청 안내와 ‘가장 먼저 맡기고 싶은 작업’ 질문이 함께 있다. CTA가 경쟁한다는 편집 가설을 세울 수 있다. 첫 후보는 마지막 질문을 제거하고 신청 안내를 유지하는 것이다. 이 후보가 실제 신청을 늘릴지는 미확인이다. 원래 게시 검토본은 변경하지 않았으며 새 후보 역시 사용자 검토가 필요하다.

## 구현과 검증 범위

`src/refinement.py`는 근거 참조·인용·본문 해시·버전·점수·사실 조건과 후보 비교를 검증한다. EvaluationAdapter는 아직 unconnected이며 manual_json으로 연결 가능하다. 출처의 진실성이나 논리적 타당성을 프로그램이 보증하지 않는다. 모델 작성·비평 호출과 영속적인 수정 횟수 추적은 런타임 연결 단계다.

`python3 scripts/mock_refinement.py`는 CTA 경쟁 문제를 합성 평가로 진단해 단일 CTA 후보를 만들고 재평가하는 흐름을 검증한다. Mock 작성·평가 데이터는 고정되어 있으며 실제 LLM의 자율 판단 성능을 검증한 결과가 아니다.
