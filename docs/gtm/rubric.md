# 사용자 반응 → 신청 전환 개선 Rubric v2

최종 목표는 **7일 캠페인 귀속 신규 사전 신청자 수**다. 판단 대상은 문안의 완성도가 아니라 ‘사용자가 왜 신청하거나 신청하지 않는가’다. 기존 문안 Rubric은 [게시 전 보조 검토](content-checklist.md)로 낮춘다. 콘텐츠 점수 상승으로 실험을 선택하거나 성공을 선언하지 않는다.

## 입력: 이전에 도달한 사용자에게서 배우기

1. 캠페인 전체 게시 이력의 실제 URL을 읽고 **이전에 게시한 모든 게시글의 댓글·답글**을 수집한다. 새 초안이 승인 대기여도 이전 글 수집을 계속한다.
2. 관련 커뮤니티의 게시글·댓글·답글을 원문 맥락과 함께 수집한다. 불편, 현재 대안, 위임 의사, 거절·불신·무관심을 함께 본다.
3. 같은 기간의 실제 신청·귀속, 가능한 경우 노출·방문을 읽는다. 댓글의 ‘신청했어요’는 메일 접수 확인 전까지 신청 수가 아니다.

자기 게시글에 대한 반응과 외부 커뮤니티 대화는 구분한다. 커뮤니티 반응은 고객 문제·표현·대안의 근거이며 우리 캠페인의 성과가 아니다. 긍정 댓글만 골라오지 않는다.

## 수집 계약

FeedbackAdapter가 대상별 조회 시각, 수집 범위, 전체/일부/접근 실패, 누락 이유와 정제된 반응을 반환한다. 상세는 [수집 계약](reaction-collection.md).

반응마다 원문 참조·게시물 연결·발생 시각·익명 작성자 키·관측 요약·분류·분류 이유·ICP 적합성을 남긴다. 같은 댓글 재조회는 새 신호가 아니다. 같은 사람의 반복 댓글은 독립적인 여러 사람의 의견이 아니다. 팀·스팸은 제외하고 작성자·ICP가 불명확하면 별도 미확인으로 보존한다.

## 판단 Rubric

각 항목은 관측됨 / 반대 근거 있음 / 미확인으로 판정하고 증거 ID를 붙인다. 합산 점수나 감성 점수를 최적화하지 않는다. 분류는 해석이며 원문 관측과 구분한다.

| 판단 축 | 확인할 질문 | 필요한 사용자 근거 | 연결할 다음 행동 |
| --- | --- | --- | --- |
| 문제 적합성 | 실제로 앱 확인이 번거로운가? | 본인 경험·빈도·현재 대안, ‘직접 하는 편이 낫다’ 등 반대 근거 | 유지 또는 고객 상황 재조사 |
| 위임 의사 | 이 일을 Mu에 맡기고 싶은가? | 구체적 요청·사용 조건·맡기지 않겠다는 이유 | 원하는 작업과 조건을 확인; 호감과 의사 구분 |
| 이해 | 기능·사전 사용 상태를 오해하는가? | 예약 성공 보장·즉시 사용으로 이해한 댓글 | 오해를 만든 설명 한 곳 수정 |
| 신뢰 | 권한·로그인·결제 우려가 신청을 막는가? | 사용을 주저하는 이유와 요구하는 증거 | 확인된 승인·권한 설명 또는 실제 데모 근거 보완 |
| 신청 마찰 | 신청하려다가 어디에서 막혔는가? | 링크·메일·신청 절차에서의 실제 혼동·실패 | 재현 후 신청 과정 한 곳 수정 |
| 전환 연결 | 반응 이후 실제 신규 신청이 생겼는가? | 같은 구간의 검증된 접수·귀속·제외 집계 | 유지·후속 실험·판단 보류 |

‘좋아요’는 가벼운 관심이며 신청 의사나 접수가 아니다. 부정 반응은 제거 대상이 아니라 반증·병목 후보다. 긍정·부정이 섞이면 둘 다 기록한다.

## 개선할 병목 선택

먼저 수집·측정 신뢰도를 확인한다. 누적 신청이 줄면 집계 정정을 점검한다. 수집하지 못했다면 무반응으로 해석하지 않는다.

선택 우선순위는 신청에 직접 가까운 **신청 마찰 → 제품 오해 → 신뢰 우려 → 문제·대상 불일치**다. 이는 초기 운영 가설이며 실제 근거와 반대 근거를 함께 검토한다.

- 같은 게시글에서 적격 외부 작성자 2명 이상이 같은 병목을 표현하고 새 작성자의 근거가 추가되면 단일 변경 실험 후보를 만든다.
- 한 사람의 반응은 맥락·재현 확인 대상으로 삼는다. 재현된 기능 오류는 별도 실제 검증 근거를 남겨 처리할 수 있다.
- 여러 댓글을 쓴 한 사람, 서로 다른 문맥의 게시글을 합쳐 ‘반복된 수요’로 부풀리지 않는다.
- 커뮤니티 근거만 있으면 고객 가설 조사로 보낸다. 우리 게시 효과나 전환 병목으로 확정하지 않는다.
- 새 관심 반응이면 유지하며 실제 신청을 확인한다. 긍정 반응이 생겼다고 매번 새 예시를 만들지 않는다.
- 같은 근거만 반복되면 유지한다. 자료 부족·도달 부족·수집 누락은 추가 관측으로 보낸다.

‘2명’은 실험 후보 우선순위를 정하는 초기 코드 규칙이며 통계적 유의성·시장 검증 기준이 아니다. 분류·ICP·원문 판단은 Adapter/에이전트가 수행하고 코어는 입력 계약과 선택 규칙을 검사한다.

## 다음 실험과 효과 판단

반응 근거 → 병목 가설 → 다른 설명 → 변경 변수 하나 → 예상 반응·신청 변화 → 관측 기간 → 유지/수정/보류 조건을 게시 전에 기록한다.

예: ‘메일 신청 방법을 못 찾겠다’는 댓글이 반복된다 → 신청 의사는 있으나 과정에서 막힐 수 있다 → 신청 안내 한 곳을 명확히 한다 → 다음 24시간 같은 혼동 반응과 실제 신규 신청을 함께 관측한다.

전후 비교에는 기간, 게시물/실험, 도달·방문 분모, 수집 범위, 신규 적격 작성자 수, 병목을 표현한 작성자 수, 실제 신청 증분, 귀속 범위를 기록한다. 작성자 수 비율을 쓰려면 분모도 수집된 범위의 적격 작성자로 명시한다. 한 사람의 반응을 전체 방문자의 반응으로 일반화하지 않는다.

- 같은 혼동 반응이 줄고 신규 신청이 늘면 ‘개선과 일치하는 관측’으로 기록한다. 시간·도달 대상 차이가 있어 인과 효과는 미확인이다.
- 댓글만 줄고 신청이 늘지 않았다면 전환 개선 미확인이다.
- 신청이 늘어도 콘텐츠별 귀속이 없다면 캠페인 수준 관심 신호다.
- 수집 누락, 표본 부족, 비교 조건 차이, 아직 결과 관측 전이면 판단 보류한다.
- 한 번에 메시지·채널·신청 과정을 함께 바꾸지 않는다. 실패한 예측과 반대 의견도 다음 실행에 전달한다.

## 구현 범위

`src/feedback.py`는 반응 수집 계약, 과거 반응 합치기, 반복·작성자 중복 처리, 출처 구분, 병목 선택, 신청 증분을 구현한다. `src/loop.py`의 `next_action`은 이 반응 판단으로 결정하며 기존 집계만의 추천은 `metric_diagnostic`으로 분리했다. 본문 점수는 다음 실험을 선택하지 않는다.

실제 원문 조회·댓글 분류·MCP 연결과 전후 비교의 종합 판단은 런타임 경계다. 코어는 인과 효과를 자동 판정하지 않고 effect=not_established로 기록한다. 현재 실제 게시 이력과 반응 연결은 없으며 합성 댓글·커뮤니티 의견으로 검증했다.
