# Mu 첫 GTM 전략

기준일: 2026-10-24. 상태: 첫 실험 방향 확정, 고객·채널·전환 검증 전.
사용자 결정: 인기 식당 예약을 첫 사용 사례로 삼고 모바일 앱 자동화의 가치를 강조한다. 지금의 전환은 사전 사용 신청이다. 구현 확장보다 GTM 요소와 기본 루프를 먼저 다듬는다.

## 1. 이번 실험의 한 문장

**인기 식당 예약 확인으로 관심을 만들고, 카카오톡으로 모바일 앱 작업을 맡기는 범용 비서 Mu를 소개한 뒤 사전 사용 신청을 받는다.**

모바일 앱을 직접 열고 확인해야 하는 수고가 메시지의 중심이다. 웹보다 모바일 앱 안의 작업을 맡기기 어렵다는 점은 이번 포지셔닝의 출발점이다. 모든 예약 서비스가 모바일 전용이라거나 웹 자동화는 언제나 쉽다는 일반적 사실로 주장하지 않는다. 특정 서비스의 앱 전용 기능은 실제 조사로 확인한다.

| 요소 | 첫 정의 | 상태 |
| --- | --- | --- |
| 제품 단계 | 실제 이용 전 사전 사용 신청 모집 | 사용자 확인 |

| 보조 지표 | 확인 가능한 노출, 방문, 신청 과정 이탈, 신청 이유 | 미연결 |
| 학습 단위 | 한 번에 ICP/채널/메시지/신청 과정 중 주요 조건 하나 | 확정 |

나이·직업·소득은 근거가 없어 타깃 조건에 넣지 않는다. ‘AI에 관심 있는 모든 사람’보다 예약을 준비하는 구체 상황을 먼저 관찰한다.

## 3. ICP를 에이전트가 판별하는 기준

다음은 조사·콘텐츠 적합성 기준이다. 공개 문제 표현만으로 구매 의사를 판정하지 않는다.

| 조건 | yes를 줄 근거 | unknown 처리 |
| --- | --- | --- |
| restaurant_intent | 특정 인기 식당이나 방문 희망 날짜·인원 등 실제 예약 의도를 본인이 표현 | 추측하지 않고 추가 관측 |
| mobile_task | 모바일 앱 안에서 예약 가능 여부를 확인해야 한다고 표현하거나 해당 흐름을 확인 | 앱 전용이라고 단정하지 않음 |
| checking_friction | 앱을 여는 일·조건 입력·여러 번 확인의 번거로움을 본인이 표현 | 좌석 없음만으로 yes 부여 금지 |
| reachable_context | 접근 가능한 게시물이며 홍보/참여 규칙을 확인 | 외부 게시 후보 대기 |

직접 고객 후보: 앞 세 조건이 yes. 특정 고객 대화에 참여할 후보: 직접 고객 후보이며 마지막 조건도 yes. 후보가 적으면 수를 채우기 위해 조건을 완화하지 않고 어느 조건이 부족한지 기록한다.

신규 모집 채널은 별도로 판정한다. 제품 소개·사전 사용자 모집이 허용된 공간에서는 모집 게시를 통해 예약 경험과 관심을 새로 확인할 수 있다. 기존 공개 글에서 적격 고객을 먼저 찾는 것은 모든 모집 게시의 필수 조건이 아니다. 모집 채널의 독자 전체가 ICP라고 간주하지 않으며, 채널 가설·도달·응답·실제 신청을 구분한다.

우선 제외: 예약 성공·좌석 선점만을 원하는 사람, 즉시 사용을 요구하는 경우, 재판매·자동 선점 요구. 신청 의사는 실제 신청 접수나 명시적인 사용 희망 응답으로 별도 확인한다. 과거 글의 문제는 현재도 유효한지 확인한다.

## 4. 메시지와 제안

메시지 순서: **익숙한 예약 상황 → 모바일 앱 조작의 수고 → 카카오톡으로 맡기는 사용 방식 → 사전 신청 안내.**

합의한 메시지 구조: 인기 식당 예약 확인 요청 예시 → 카카오톡으로 모바일 앱 작업을 맡기는 제품 설명 → 배송 조회·장바구니 등 활용 범위 → Mu 사전 신청. 정확한 본문은 [실험 문서](experiment.md)에 보존한다. 같은 콘텐츠에서 사전 신청 단계임을 밝힌다.

사용 예시: ‘이번 토요일 저녁, 두 명 예약 가능한 시간 있는지 확인해줘.’ 예시는 제품 구상/소개에 기반한 요청 문장이다. 실제 실행 화면·성공 결과·고객 후기로 포장하지 않는다.

지금 제안하는 보상은 먼저 사용해볼 기회를 신청하는 것이다. 확인되지 않은 제공일, 대기 순번 우대, 할인, 확정 이용권은 만들지 않는다. ‘모바일 앱 자동화’는 차별점 설명에 쓰고, 첫 문장은 고객이 하는 일로 시작한다.

예약 가능 여부 조회와 예약 확정을 구분한다. 결제·예약 확정은 제품 소개상 별도 승인 대상이며, 자동 선점·반복 감시·경쟁자보다 빠른 예약·예약 성공은 이번 약속에 포함하지 않는다.

## 5. 유입에서 신청까지

1. 공개 원문에서 ICP 조건을 확인하고 후보 최대 10개를 기록한다.
2. 문제 적합성과 참여 규칙이 확인된 채널 한 곳을 선택한다. 독자 수나 신규 계정의 자연 유입을 가정하지 않는다.
3. 해당 맥락에 맞춘 공개 콘텐츠 하나를 작성한다. 관계가 있는 제품임을 숨기지 않는다.
4. 사람이 정확한 본문·계정·채널을 승인한 뒤 게시하고 실제 URL·시각을 기록한다.
5. 한국어 제품 페이지에서 준비 단계와 신청 방법을 안내한다. 해당 페이지 내용·수정 권한은 미확인이다.
6. 실제 신청 접수를 확인한다. 가능하면 ‘맡기고 싶은 식당/조건’을 선택적으로 수집해 다음 메시지에 활용하되 필수 질문을 늘리지 않는다.
7. 실제 신청이 캠페인에서 왔는지 확인하고 기존 신청자·중복·테스트·스팸을 제외한다.

신청 버튼 목적지는 미확인이다. 공개 지원 주소를 신청 주소로 대신 확정하지 않는다. 이메일 방식이면 제목 코드 MU-KO-001 또는 선택적 유입 경로 응답으로 귀속하고, 메일 작성 화면을 연 것과 실제 수신을 구분한다. attribution.verified가 true가 되기 전에는 추적 완료라고 하지 않는다.

## 6. 첫 루프

이전 실행의 관측·미측정·다음 변경 읽기
→ 고객 문제 원문 확인
→ 인기 식당 × 모바일 앱 조회 메시지 하나 작성
→ 사람 검토
→ 승인 범위 내 게시
→ 실제 신청·제외·귀속 확인
→ 관측과 해석 분리
→ 다음 주요 변경 하나 선택
→ 다음 날 반복.

매 실행 산출물은 원문 근거, ICP 판정, 콘텐츠와 asset_id, 승인·게시 영수증, 신청 스냅샷, 다음 변경이다. 연결되지 않은 단계는 pending/unconnected로 기록한다. 지금은 Adapter 계약 기반 설계이며 실제 고객 조사·게시·전환 측정은 완료되지 않았다.

## 7. 무엇을 보고 바꿀 것인가

| 관측 | 가능한 해석 | 다음 행동 하나 |
| --- | --- | --- |
| 문제에 맞는 고객 원문을 못 찾음 | ICP 조건 또는 접근 경로가 부적절할 수 있음 | 불충족 조건 하나를 확인; 고객 문제를 임의로 만들어내지 않음 |
| 배포/노출이 없음·미측정 | 메시지 평가 근거 없음 | 채널 접근 또는 노출 확인 |
| 노출 표본 부족 | 판단 보류 | 같은 메시지로 배포 경로 하나 점검 |
| 노출이 있으나 방문 부족 | 상황/가치 설명이 맞지 않을 수 있음 | 첫 문장 하나 변경 |
| 방문이 있으나 신청 없음 | 신청 마찰·준비 단계·가치·추적 중 원인 미확정 | 신청 경로부터 점검해 병목 하나 선택 |
| 실제 귀속 신청 발생 | 이 제안에 관심을 표현한 사람이 있음 | 신청 이유에 맞춰 요청 예시 하나 변경 |

설정의 노출 100·방문 20은 초기 운영 판단용 가정이다. 통계적 유의성이나 성공 기준이 아니다. 인원이 적으면 정성적인 신청 이유를 함께 기록하고 인과 효과를 단정하지 않는다. 누적 신청자 수를 일별로 더하지 않는다.

## 8. 7일 운영 순서

- 시작 전: 실제 접수·귀속·기존 신청자 기준과 7일 측정 구간을 확정한다. 달력 날짜는 행사 공지 확인 후 고정한다.
- 1일차: 고객 문제와 채널을 확인하고 첫 콘텐츠를 게시한다.
- 2일차: 게시·방문·접수의 측정 누락을 먼저 확인한다.
- 3–6일차: 하루 한 번 기록을 읽고 주요 조건 하나만 바꿔 반복한다. 신청자 후속 연락은 별도 승인 범위가 있을 때만 한다.
- 7일차: 종료 시각까지 접수된 캠페인 누적 신청을 확정하고 제외 내역·정제된 증거·변경 이력을 정리한다.

최초 1회 수동 시작 후 하루 한 번 자동 루프가 목표다. SchedulerAdapter·실행 런타임은 아직 미연결이며 새 게시물은 매번 사용자 최종 검토를 거친다.

## 9. 아직 다듬을 결정

우선순위는 실제 접근 가능한 첫 채널 → 해당 앱에서 검증 가능한 지원 범위 → 신청 절차와 귀속 → 첫 문구의 구체성이다. 지금 확정한 ICP·가치 제안은 초기 가설이며, 외부 사실이 필요한 항목은 추정으로 채우지 않는다. 사전 신청 수 목표는 도달 가능한 모수 확인 전 임의로 만들지 않는다.

## 계정·독자 0 조건 갱신 (2026-10-24)

사용자가 기존 게시 계정과 참여 커뮤니티가 없다고 확인했다. 기존 네트워크 활용을 전제하지 않고 신규 계정·프로필·첫 게시물·도달 경로를 설계한다. [신규 배포 설계](zero-audience-distribution.md)를 따른다. 이후 사용자가 Threads 계정 생성 완료를 확인했다. 에이전트의 로그인·프로필 설정·게시 자체는 미실행이다.

## 최신 결정

사용자가 첫 채널을 Threads로 선택했다. 기존 Disquiet 주경로 제안은 종료한다. 최초 1회 수동 시작 후 하루 한 번 자동 반복을 목표로 하며 게시물 최종 검토는 매번 유지한다. SchedulerAdapter는 미연결이다. 발표 문서는 작성 예정에서 [지속 갱신 문서](presentation.md)로 전환했다.
