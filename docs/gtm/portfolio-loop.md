# 높은·낮은·새 가설을 병렬 비교하는 루프

최종 설계: 복잡한 확률 배분 없이, 실제 반응으로 가설을 만들고 같은 기회의 병렬 실험을 반복한다. 음식 예약은 시작점이며 배송·장바구니·메일 등으로 확장한다. 기존 반응 수집·단일 게시 검토 코어 위에 가설·계정별 배포를 묶는 비교 코어를 둔다.

## 한 번의 실행

1. 모든 과거 게시물 댓글·답글과 관련 커뮤니티 반응, 실제 신청 결과를 수집한다.
2. 가설 생성 에이전트가 높은 반응의 이유, 낮은 반응의 원인, 다른 앱 작업의 기회를 가설로 만든다.
3. 별도 검토 에이전트가 근거·반증·신청 지표 연결·비교 조건을 확인한다. 생성 에이전트는 스스로 최종 통과시키지 못한다.
4. 콘텐츠 작성 에이전트가 가설별 게시물을 만들고 사실·사전 사용 상태·신청 경로를 확인한다. 사용자 승인 후에만 공개한다.
5. 높은 쪽, 낮은 쪽 또는 그 개선안, 새 영역에 각각 한 슬롯을 배정한다. 첫 실행에는 기존 결과가 없으므로 초기 가설을 균등하게 시험한다.
6. 계정과 가설을 교차 배치한다. 예: A계정이 오늘 높은 쪽이면 다음 날에는 다른 슬롯을 맡는다. 계정별 독자 차이를 가설의 효과로 오해하지 않는다.
7. 같은 관측 기간이 끝나면 반응과 실제 신규 신청을 나란히 확인한다. 유지·재현·개선·확장을 결정하고 새 가설을 만든다.

## 높은·낮은 수치의 의미

최종 판단 지표는 확인된 신규 신청이다. 코어는 동일 관측 구간의 배포당 신청 수를 계정별로 비교한다. 계정·시간 조건별 최소 2회 성숙 관측이 있어야 높은·낮은 비교 후보로 삼는다. 관측 시간이 지나지 않았거나 데이터가 없으면 낮은 쪽이 아니다. 동률이면 승자를 만들지 않는다.

댓글 반응은 따로 읽는다. 문제 경험·위임 의사·오해·신뢰·신청 마찰, 적격 작성자 수·관심 표현·방문을 근거로 원인을 설명한다. 반응이 높아도 신청이 낮으면 신청 경로나 제품 신뢰를 점검하고, 반응은 적어도 실제 신청이 높으면 해당 가설을 성급하게 버리지 않는다. 댓글 수와 신청 수를 임의의 가중 합산 점수로 만들지 않는다.

신청 귀속이 캠페인 수준에만 있으면 실험군 성과 비교는 보류한다. 이때도 반응으로 가설을 만들고 균등 탐색은 가능하나 신청 기준 높은·낮음이나 승자라고 주장하지 않는다. 현재 코어의 정량 비교는 검증된 배포별 신청을 기준으로 하며, 반응 해석·낮은 쪽 개선안 생성은 에이전트 Adapter 책임이다.

## 병렬 비교의 조건

- 등록된 운영 계정만 사용한다. 계정은 게시 주체이고 고객 신원과 구분한다. 현재 실제 계정은 @mu.agent 하나이며 추가 계정·연결은 준비되지 않았다.
- 계정 3개가 연결되면 높은·낮은·새 가설을 같은 배치에 계획한다. 1~2개면 슬롯을 순환하고 완전한 동시 비교라고 표시하지 않는다.
- 초기 기준은 계정별 하루 1회, 관측 기간 24시간, 병렬 최대 3슬롯이다. 설정으로 바꿀 수 있으며 효과가 입증된 최적값은 아니다.
- 계정별 가설을 교차 배치해 한 계정에 특정 가설이 고정되지 않도록 한다. 그래도 시점·독자 차이가 있어 인과 효과를 보장하지 않는다.
- 가설·제안이 달라지면 새 arm_id, 문안 버전은 asset_id, 계정별 게시 실행은 deployment_id를 갖는다.
- 낮은 가설을 곧바로 삭제하지 않는다. 개선안은 부모 가설을 연결하고 기존 성과를 물려받지 않는다.

## 에이전트와 교체 가능한 Rubric

| 역할 | 판단 기준 | 설정 |
| --- | --- | --- |
| 가설 생성 | 사용자 반응 근거, 검증 가능성, 새로운 검증 축 | hypothesis_generator.v1.json |
| 가설 검토 | 증거 품질, 신청 지표 연결, 계정·시각·귀속 비교 가능성 | hypothesis_reviewer.v1.json |
| 콘텐츠 작성 | 가설 유지, 제품 주장 근거, 신청 안내·귀속 | content_writer.v1.json |
| 결과 검토 | 관측 기간 완료, 반대 근거·혼동 요인, 다음 실험 | learning_reviewer.v1.json |

파일은 config/rubrics/에 있고 config/portfolio.json에서 역할별 경로를 선택한다. AgentAdapter는 task·rubric·evidence를 받고 평가 결과를 반환한다. JSON 입력과 Mock 구현이 같은 계약을 사용한다. 평가마다 기준 버전·내용 해시·대상 해시·항목별 이유·증거를 기록한다. 기준을 교체하면 과거 평가를 새 기준의 통과로 재사용할 수 없다. Rubric 점수는 실험 준비 여부이며 신청 보상이 아니다.

## 비교 이후 새 가설

관측상 높은 가설이 여러 계정 조건에서도 유지되면 결과 검토 에이전트가 운영 기준 가설로 기록한다. 이는 관측한 비교군 안의 판단이며 미관측 가설까지 이긴다는 뜻이 아니다. 높은 가설은 다음 비교의 기준으로 유지하고 낮은 가설의 개선안과 다른 앱 영역 확장을 생성할 수 있다.

같은 결과를 매번 새 발견으로 처리하지 않는다. 생성 요청은 같은 사건에 한 번 만들고 완료 전에는 재시도할 수 있다. 초기 활성 가설 한도는 5개다. 한도가 차면 다음 생성은 검토 대기로 두고 어떤 가설을 보류할지 사람이/검토 에이전트가 결정한다. 확률 최적화나 자동 저성과 제거는 없다.

## 신청 귀속과 관측

한 사람은 캠페인 전체에서 한 번만 센다. 배포별 식별 코드가 실제 접수까지 보존되어야 한다. 최초로 검증된 배포 코드를 귀속 기준으로 사용하고 모호한 신청은 캠페인 전체에만 기록한다. 여러 배포에 같은 신청 credit_id를 넣으면 코어가 거부한다. 실제 사람의 중복 판별은 수신 Adapter 책임이며 익명 credit_id의 원본 매핑은 private 영역에 둔다.

배포 후 24시간 구간이 끝나고 실제 접수·기존 제외·중복 제거·완전성이 확인되어야 결과를 비교한다. 미완료 구간은 0이 아니다. 7일 종료 때문에 24시간이 잘린 배포는 완전한 구간과 비교하지 않으며 캠페인 전체 접수 집계와 분리한다. 같은 영수증의 재입력은 중복 집계하지 않고 정정은 별도 감사 후 재구축해야 한다.

## 현재 구현과 남은 연결

`src/portfolio.py`는 역할별 Rubric 검증, 가설 등록, 비교 슬롯 계획, 정확한 사람 승인·게시 영수증 검사, 완료 관측 집계, 높은·낮은 비교, 새 가설 요청을 수행한다. `src/feedback.py`는 반응 정제·병목 판단을, `src/loop.py`는 기존 단일 실행 기록을 담당한다. 반응 원문을 가설 에이전트 입력으로 변환하는 실런타임은 미연결이다.

`python3 scripts/mock_portfolio.py`는 3가설·3합성 계정 → 7일 관측 → 높은·낮은 비교 → 개선안·메일 요약 확장 생성 → 같은 슬롯의 병렬 계획을 검증한다. 실제 병렬 네트워크 게시, 실제 모델 품질, 실제 신청 증가를 검증한 것은 아니다. 생산 운영에서는 배치 예약·동시성 잠금·uncertain 게시 재조회·모델 호출·수집 연결이 필요하며 현재 기존 단일 실행 계약과 Mock으로만 다뤘다.
