# 첫 캠페인 신청 귀속 준비

campaign_id: MU-KO-001 / experiment_id: EXP-MU-KO-001
상태: 귀속 방법 제안 완료, 사용자가 제목 코드 의미를 질문하여 설명 요청 상태. 채택·수신·기준·기간 검증 전. 실제 신청 수는 미측정(null).

## 확인한 경로

2026-10-24T07:33:52.114392+00:00 관측한 [공개 HTTP 증거](../ref/evidence/mu-cta-20261024.json)에 따르면:

- [한국어 Mu 페이지](https://mu.pairful.ai/ko)의 사전 신청 버튼 href는 `/w/go/ko`다.
- [신청 경로](https://mu.pairful.ai/w/go/ko)는 HTTP 302로 `mailto:support@pairful.ai`에 연결한다.
- 기본 제목은 `무 먼저 써보고 싶어요`, 본문은 사전 사용 희망 인사와 주로 쓰는 메신저를 묻는 입력 안내다.
- 이 경로에 `campaign_id=MU-KO-001&utm_campaign=MU-KO-001`을 추가해도 반환된 mailto의 제목·본문에 해당 코드가 없었다. 서버 쪽 방문 분석 여부까지 확인한 것은 아니다.
- 폼 제출·메일 발송·수신함 조회를 하지 않았다. 메일 작성 화면을 여는 것과 실제 신청 접수는 다르다.

Gmail 읽기 MCP 도구는 목록에서 확인됐지만, 연결된 계정이 이 지원 수신함을 읽을 수 있는지는 확인하지 않았다. 사용자의 지시에 따라 MCP 접근 가능을 설계 가정으로 두고 구체 인프라 연결은 미룬다.

## 권고하는 최소 방법: 신청 메일 제목의 캠페인 코드

랜딩을 수정하지 않고, 게시물에 제품 소개 링크와 캠페인 코드가 들어간 신청 메일 링크를 함께 둔다. 한 캠페인에서 같은 제목 코드를 유지한다. 현재는 campaign 수준으로만 귀속하고 콘텐츠별 전환 비교를 하지 않는다.

정확한 제목:

```text
[MU-KO-001] 무 먼저 써보고 싶어요
```

권고 CTA 문구:

> Mu 사전 사용을 신청해 주세요. 메일 작성 화면이 열리면 내용을 확인하고 보내주시면 됩니다.

게시물의 제품 소개 링크는 `https://mu.pairful.ai/ko`를 유지한다. 신청 링크는 아래 URI를 사용한다. 이 문서에서는 생성·디코딩만 검증했으며 링크를 실행하거나 발송하지 않았다.

```text
mailto:support@pairful.ai?subject=%5BMU-KO-001%5D%20%EB%AC%B4%20%EB%A8%BC%EC%A0%80%20%EC%8D%A8%EB%B3%B4%EA%B3%A0%20%EC%8B%B6%EC%96%B4%EC%9A%94
```

본문은 사전 입력하지 않는다. 제목 자체에 사전 사용 신청 의사가 들어 있으며, 앱 작업 질문에 대한 답변은 선택 사항이다.

메일 링크를 허용하지 않는 채널에서는 같은 방법을 수동으로 안내한다: **“제품 페이지에서 먼저 써보기를 누른 뒤, 신청 메일 제목에 [MU-KO-001]을 넣어 주세요.”** 코드 입력이 추가 마찰이며 누락될 수 있음을 기록한다. 앱에 메일 계정이 설정되지 않은 경우 작성 화면이 열리지 않을 수 있어 `support@pairful.ai`와 제목을 텍스트로도 제공한다.

캠페인 코드를 빼거나 바꾼 신청은 추정해서 귀속하지 않는다. 기본 제목의 메일은 접수 확인 시 출처 불명으로 따로 집계한다. 명시적인 유입 자기보고를 별도로 받더라도 현 설정은 `email_subject_code`이므로 그 성과를 몰래 합산하지 않는다. 자기보고를 포함하려면 방법과 한계를 먼저 변경 기록으로 남기고 Adapter 계약을 맞춘다. 공유된 신청 링크가 다른 곳으로 전달될 수 있으므로 제목 코드는 캠페인 연관의 증거이며 특정 게시물 노출의 증거는 아니다.

| 항목 | 확정 내용 | 현재 |
| --- | --- | --- |
| 수신 접근 | support 수신함 또는 동일 메일이 수신되는 별칭·전달 경로를 읽을 수 있음 | assumed, 미검증 |
| 내부 테스트 | 승인된 테스트 메일의 코드·수신·발신자·시각을 확인하고 테스트로 제외 | 미실행; 발송 승인 없음 |
| 기존 신청자 기준 | 시작 직전까지 접수된 모든 기존 사전 신청자를 기존 명단으로 고정; 제목 코드 없는 과거 신청도 포함 | 미확인 |
| 기간 | timezone Asia/Seoul, 시작 포함·종료 제외, 정확히 7일; 행사 기간과의 관계 확인 | start/end null |
| 신청 정의 | 본인이 사전 사용을 명시적으로 요청한 실제 수신 메일 | 계약 확정, 실제 자료 미검증 |
| 중복 기준 | 캠페인 전체의 동일인 확인 규칙과 이메일 비교 규칙 | 담당자 확정 필요 |

미완료 항목을 추정으로 채우지 않는다. 기준 명단 접근이 없으면 신규 여부를 검증할 수 없으므로 주 지표를 measured로 내보내지 않는다. 제목 코드와 메일함 검색만 구현됐다고 측정 완료가 되지 않는다.

## MeasurementAdapter 내부 처리 순서

원본과 개인 식별자는 MCP/`private/` 안에서만 관리한다. 코어는 이 처리를 직접 구현하지 않는다.

1. 캠페인 시작 이전의 기존 신청자 기준을 고정하고 비공개 기준 버전 참조를 남긴다.
2. 고정 기간 시작부터 이번 집계 마감 `through` 직전까지 실제 수신된 신청 후보를 읽는다. 최신 스냅샷마다 캠페인 전체 기간을 중복 없이 재집계한다.
3. 본인의 사전 사용 요청인지 확인한다. 전달본, 자동응답, 단순 문의·답장, 반송은 신규 신청으로 세지 않는다. 메일 수신 시각을 기준으로 삼고 발신자가 작성한 Date 헤더만 믿지 않는다.
4. 테스트 → 스팸 → 기존 신청자 → 동일 캠페인의 중복 순으로 제외 사유 하나를 지정한다. 중복 레코드의 유효한 귀속 근거는 동일인 기록에 연결한 뒤 중복 수만 제외하므로, 최초 신청에 코드가 없었다는 이유로 나중의 명확한 귀속 근거를 버리지 않는다. 테스트 발신자·메시지 ID 목록은 비공개로 보관한다. `excluded`는 제외된 신청 후보 레코드 수이며 신규 고유 신청자 수와 다른 단위다.
5. 남은 신규 신청자는 실제 제목의 독립된 `[MU-KO-001]` 토큰으로 캠페인에 귀속한다. 본문 인용·답장 이력·검색 스니펫에만 있는 코드를 근거로 삼지 않는다. 코드 없는 신규 신청자는 unknown_source_signups에 따로 센다.
6. 사람 단위로 정리한다. 같은 이메일의 반복 신청은 한 건, 알려진 동일인의 복수 이메일도 한 건이다. 이메일 앞뒤 공백 및 도메인 정규화와 대소문자 비교 규칙을 먼저 고정하며, Gmail 점/플러스 제거를 다른 제공자에 일괄 적용하지 않는다. 동일인 여부를 모르는 복수 이메일은 그 제한을 명시하며 ‘완벽한 사람 단위 판별’로 보고하지 않는다.
7. 캠페인 중 나중에 명확한 귀속 근거가 생긴 사람은 최신 스냅샷에서 출처 불명에서 귀속으로 재분류할 수 있다. 이때 정정 근거와 시점을 기록하고 같은 사람을 두 집계에 동시에 넣지 않는다. 기간 밖 접수는 기간 안 신규 신청으로 소급하지 않는다.
8. 정제된 집계·증거 참조만 코어에 전달한다. 누적값을 일별 합산하지 않는다. 잘못 포함된 신청을 정정하면 누적 수가 줄 수도 있으므로 변경 사유를 별도 정제된 증거에 남긴다.

스팸/반송/단순 문의처럼 신청 후보가 아닌 메일을 제외 집계에 포함할지는 운영 기준에서 고정한다. 원시 수신 메일 총수와 제외 집계의 합이 반드시 일치하는 것으로 해석하지 않는다. 핵심은 실제 요청·신규·귀속·동일인 기준의 일관성이다.

## 코어에 넘기는 입력 계약

현재 코어 `src/loop.py`가 받는 MeasurementAdapter 입력 기준이다. 상세 메일 처리와 중복 제거는 Adapter 책임이다. 현재 사용할 수 있는 안전한 입력은 다음뿐이다.

```json
{"status": "unconnected"}
```

연결을 준비하고 있지만 검증이 끝나지 않았으면 `{"status":"pending"}`을 사용한다. 두 경우 코어 결과의 `new_attributed_signups`와 `unknown_source_signups`는 null이다. 아직 검증하지 않은 값을 0으로 제출하지 않는다.

검증 후 `status=measured` 입력은 다음 필드를 가진다. 아래 표는 스키마 설명이며 실제 신청 스냅샷이 아니다.

| 필드 | 값·조건 |
| --- | --- |
| status | `measured` |
| campaign_id | `MU-KO-001` |
| window | 설정과 정확히 같은 start/end ISO 8601 시각; 시간대 포함, 정확히 7일 |
| observed_at | 실제 관측 시각; 미래 시각 금지 |
| through | 이번에 완전히 수집한 접수 마감 시각, 시작 이상·종료 이하·관측 시각 이하 |
| cumulative | true; start부터 through 직전까지의 캠페인 누적 |
| baseline_verified | true; 기존 신청자 기준을 확인했을 때만 |
| receipt_verified | true; 실제 수신 증거를 확인했을 때만 |
| dedup_scope | `campaign` |
| source_method | `email_subject_code`; 설정 method와 일치 |
| new_attributed_signups | 귀속된 고유 신규 신청자 수, 0 이상의 정수 |
| unknown_source_signups | 같은 수신 범위에서 확인한 출처 불명 고유 신규 신청자 수 |
| excluded | existing/duplicate/test/spam의 정수 집계, 위 처리 기준 따름 |
| evidence_refs | 정제된 증거 ID 배열; `EV-` 뒤 영숫자·하이픈·밑줄만 |
| auxiliary | impressions/visits. 측정 안 됐으면 각각 null |

측정 완료 후 신청이 없으면 0이 유효하다. 수신함 접근 없이 ‘검색 결과가 없을 것’이라고 가정한 0은 유효하지 않다. `observed_at`은 데이터를 읽은 시각, `through`는 누락 없이 집계를 마친 시각이다. 메일 검색의 날짜 경계나 페이지 제한만으로 완전성을 가정하지 않고 타임스탬프와 페이지 전체를 확인한다.

현재 코어는 기초 필드·기간·귀속 설정·증거 ID를 검사한다. 수신함 범위, 원본의 진위, 신청자의 동일인 여부, 필드 집계 산식까지 검증해주지는 않는다. 그 확인 책임을 Adapter 담당자와 사람 검토에 남긴다.

## 증거와 개인정보

공개 Git 기록: 기간·관측 시각·누적 집계·제외 기준·방법의 한계·정제된 증거 ID 및 설명. 공개 제품 지원 주소 외에 신청자 이메일, 이름, 원본 제목/본문, 메시지 ID, 계정 식별자, 해시화된 개인 식별자도 넣지 않는다.

비공개 처리: 기존 신청자 기준, 수신 메일, 동일인 매핑, 테스트 명단, 제외 판정 근거. `private/`는 Git에서 제외된다. 정제된 증거마다 비공개 원본을 확인할 수 있는 내부 대응표를 유지하되 공개 기록에는 식별자를 복제하지 않는다.

현재 관측 증거 `EV-MU-CTA-20261024`는 **신청 링크의 목적지 증거**다. 실제 신청 수신이나 신규 귀속 성과의 증거로 재사용하지 않는다.

## 다음 실행 조건

게시 담당은 제목 코드 방식과 실제 채널의 mailto 지원 여부를 반영한 최종 본문을 준비한다. 측정 담당은 수신 접근·기존 신청자 기준·기간을 확인한다. 이후 승인된 내부 테스트로 코드가 보존되는 접수와 제외를 검증한다. 이 문서 작성 시점에는 모든 실제 성과가 미측정이고 외부 발송·연결·일정 고정은 실행하지 않았다.

## Threads 결정 이후 상태

첫 채널은 Threads로 확정됐다. 제목 코드의 의미는 내부 캠페인 식별이며 할인·혜택·신청자 번호가 아니다. 현재 Threads 공개 초안에는 이 코드를 넣지 않았고 기존 랜딩 링크만으로는 귀속이 보장되지 않는다. 이 문서의 mailto 방식은 준비된 제안이며 실제 채택·플랫폼 지원·수신 검증은 대기다.
