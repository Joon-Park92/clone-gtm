# 최초 시작 이후의 일별 반복 운영

사용자 결정: 처음 한 번 수동으로 시작하고 이후 하루 한 번 반복한다. 현재는 목표 운영 방식이며 스케줄러·외부 실행 런타임은 미연결이다. 로컬 코어 실행과 지시문 작성만으로 자동 반복이 활성화되지는 않는다.

## 실행 계약

1. 시작 전: Threads 계정, 실제 접수·귀속, 기존 신청자 기준, 7일 측정 구간, 외부 게시 승인 경로를 고정한다.
2. 최초 수동 시작: 한 번의 에이전트 실행을 호출하고 SchedulerAdapter에 24시간 간격 요청을 전달한다. 등록 영수증이 있어야 scheduled=true로 기록한다.
3. 매일 반복: 이전 실행 → 고객·게시 반응 조사 → 실제 신청 집계 → 다음 변경 결정 → 다음 콘텐츠 초안 → 검토 요청 → 기록·발표 문서 갱신.
4. 게시 승인 대기: 관측·분석·기록은 계속한다. 승인 전 새 게시·답글·DM·메일을 실행하지 않는다. 같은 대기 건을 중복 요청하지 않는다.
5. 승인된 게시: 승인한 버전·계정·채널에 한해 실행하고 영수증을 기록한다. 결과 불확실 시 확인부터 하고 재게시하지 않는다.
6. 종료: 고정 7일 종료 시 최종 접수 스냅샷을 수집하고 발표 문서를 갱신한 뒤 일별 반복을 멈춘다.

## SchedulerAdapter가 맡을 일

입력: campaign_id, 시작·종료, 24시간 주기, 실행 지시 prompts/run-loop.md, 작업 폴더, 한 번에 실행 하나, 승인 대기 정책.
출력: 등록 여부, scheduler_job_id, 다음 실행 시각, 최근 실행 결과. 등록 실패·미연결이면 자동 실행 중이라고 표시하지 않는다.

스케줄러는 에이전트 런타임을 호출해야 한다. src/loop.py만 반복 실행하면 기존 JSON과 설정을 기록할 뿐 새로운 조사·추론·콘텐츠 작성이 생기지 않는다. 런타임은 각 Adapter에서 최신 데이터를 받아 실행기 입력을 갱신하고, 콘텐츠와 발표 문서를 쓰는 역할을 수행한다. 현재는 그 연결을 구체 인프라 뒤로 유보했다.

## 연결 전 상태

config.schedule.requested_mode=manual_start_then_daily, driver=unconnected, connected=false. 실행 결과는 automatic_pending_connection, scheduled=false다. suggested_at은 제안 시각이며 예약 성공 증거가 아니다. 기존 첫 로컬 실행의 manual 표시는 당시 이력으로 남긴다.

## 발표 문서 갱신

매 실행과 주요 결정 후 docs/gtm/presentation.md의 기준 시각·현재 상태·관측·학습·다음 행동을 갱신한다. 완료한 조사·테스트와 실제 게시·고객 성과를 분리한다. 새 증거가 없으면 성과 숫자를 만들지 않는다. 자동 런타임 연결 전에는 진행 중인 세션에서 에이전트가 갱신하며 세션 밖 자동 갱신은 아직 없다.

## Mock 검증 완료

`python3 scripts/mock_loop.py`가 한 번의 수동 시작과 7회의 일별 가상 tick을 재현한다. 실제 코어의 파일 Adapter 경계를 통해 승인·게시·집계·다음 문안·이력을 확인한다. 7일 종료 뒤 tick을 만들지 않으며 실제 scheduler_job_id나 외부 등록은 없다. 검증 경로: [Mock 보고서](../../runs/mock/DEMO-20261024T075844-295138/report.md). 실런타임·영속 예약·실API 오류는 이 검증 범위 밖이다.
