# 관측 → 비평 → 수정 → 재평가

먼저 docs/gtm/rubric.md, config/loop.json, 최근 실행, 제품 근거, 게시 검토본을 읽는다. 사용자 승인·측정 기간·KPI·Rubric 버전은 임의로 바꾸지 않는다.

1. 이전 예측과 최신 관측을 대조한다. 누적 스냅샷을 합하지 않는다. 새 증거가 없는 반복 호출이면 유지하고 종료한다. 원문·시각·분모·귀속 범위를 기록한다.
2. 작성자 설명을 가리고 초안과 근거만으로 비평한다. 근거의 내용이 실제 주장을 뒷받침하는지 확인한다. 사실 조건부터 판단하고 각 Rubric 항목에 0/1/2/null, 이유와 증거 ID를 붙인다. 사실 확인 실패를 문체 수정으로 덮지 않는다.
3. 가장 약한 항목 하나를 선택한다. 그 문제가 전환을 방해할 수 있다는 가설, 다른 설명 하나, 실제로 관찰할 결과, 유지 조건·중단 조건을 적는다. 실제 수요 관측이 없으면 편집 가설임을 표시한다.
4. 변수 하나만 수정한다. 문안 diff와 부모/후보 해시를 보존한다. 수정 횟수는 같은 기준본의 이전 기록에서 계산한다. 이미 두 번 수정했거나 기준을 충족했다면 종료한다.
5. 동일 Rubric과 같은 근거 범위로 후보를 비평한다. 점수를 높이려고 평가 근거를 새로 지어내지 않는다. src/refinement.py의 compare 계약으로 판정한다. 원본과 후보, 평가 전체를 정제된 실행 artifact에 보존한다.
6. 후보가 나아졌다면 최종 게시 검토본을 준비한다. 사람 승인 전 게시하지 않는다. 승인 후 변경하면 다시 검토받는다. 점수 상승은 실제 전환 개선이라고 쓰지 않는다.
7. 게시 후 신청·도달·혼동 발언을 관측해 예상과 비교한다. 실패/불확실도 남긴다. retain/observe/revise/audit와 이유를 기록하고 다음 실행에 전달한다. 계획·활동 이력·발표 문서를 갱신한다.

연결이 없으면 판단 가능한 범위만 수행하고 unconnected/미측정을 기록한다. Mock 입력은 mock 디렉터리에 격리한다. 외부 조회·게시·모델 호출이 수행됐다고 추정하지 않는다.
