# 반응 기반 병렬 가설 실험

config/portfolio.json, docs/gtm/portfolio-loop.md, 이전 실행·게시·반응·접수 증거를 읽는다.

1. 모든 이전 게시글의 댓글·답글과 커뮤니티 반응을 수집하고 높은·낮은 수치의 원인을 설명한다. 접수 미확인과 0, 도달 부족과 수요 부족을 구분한다.
2. 역할별 Rubric 경로를 로드한다. 가설 생성 에이전트가 검증 가능한 주장·반응 근거·예상·반증 조건을 만든다. 음식 예약 밖의 앱 작업도 허용한다.
3. 별도 가설 검토 에이전트가 증거·신청 지표 연결·계정 및 귀속 비교 가능성을 평가한다. 생성자가 스스로 최종 통과시키지 않는다.
4. 가설별 콘텐츠를 만들고 콘텐츠 Rubric으로 확인한다. 후보·Rubric 버전·평가·계보를 보존한다.
5. 초기에는 균등하게, 비교 자료가 생기면 높은·낮은/낮은 개선안·새 가설을 같은 슬롯으로 계획한다. 운영 계정을 교차 배치하고 계정별 게시 한도를 지킨다.
6. 각 정확한 본문·링크·첨부·계정·시각 범위에 대해 사용자 승인을 받는다. 배치 승인은 포함한 개별 항목이 명확해야 한다. 일반 진행 지시를 게시 승인으로 쓰지 않는다.
7. 실제 URL·시각을 기록하고 같은 관측 기간 뒤 반응·신청을 확인한다. uncertain은 재조회하며 재게시하지 않는다. 일정·외부 연결이 없으면 실제 병렬 실행이라고 표시하지 않는다.
8. 결과 검토 에이전트가 높은·낮은·동률·관측 부족을 판정한다. 낮은 가설을 자동 폐기하지 않고 원인 확인·개선안을 남긴다. 다른 앱 작업의 새 가설도 실험 후보로 만든다.
9. 활성 가설 5개 예산, 생성 요청 중복, 전역 신청 중복을 확인한다. 같은 관측에서 같은 가설을 반복 생성하지 않는다. 발표·PLAN·활동 이력·실행 artifact를 업데이트한다.

기존 src/loop.py만 반복 호출하면 이 다가설 역할 흐름이 자동 실행되지 않는다. 실모델·수집·배치 실행 연결은 별도다. 현재는 scripts/mock_portfolio.py로 계약과 판단을 검증한다.
